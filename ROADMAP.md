Have another developer follow the installation and workflow instructions. Record where they needed help and fix those steps. Observe whether the result helps answer the original debugging question; a large graph or a successful installation alone does not establish that value.

Use the results of the previous milestones to write a precise support statement: browser and versions, application patterns, required source or runtime integration, supported interventions, and known stopping points.

Before publishing the candidate:

- Verify installation and build from the candidate's source and lockfiles without the old prototype directory, inherited build outputs, Desktop, or a closed resolver. Reuse bootstrap verification when it still applies to the candidate; rerun checks affected by later changes.
- Run the relevant automatic checks and actual UI workflow checks. Distinguish skipped, blocked, unsupported, and passing results as defined in [validation](docs/validation.md).
- Confirm that required source, dependency, and asset licenses and notices match the distributed contents. Keep effective licensing explicit; follow [licensing](docs/licensing.md).
- Check data handling, the boundaries used by the browser and project connection, and passive import behavior. Confirm a working private route for sensitive reports under [SECURITY.md](SECURITY.md).
- Publish verified setup instructions, one reproducible example, known limitations, and a short demonstration of the supported workflow.

An IDE-connected developer preview is a valid intermediate scope if it is useful and clearly named. It must not be described as a browser-only alpha. Publishing the source repository, publishing a preview, and meeting this roadmap's alpha scope are distinct outcomes.

## Work after the first alpha

Prioritize the next mechanism from failures observed in the selected cases and user investigations. Candidates include additional transformations, cache origins, repeated exchanges, async boundaries, or adapters, but none is assumed broken or absent without inspecting the implementation. Each addition needs a specific supported claim and an independent control.

Add another framework or store when there is a concrete application to support. Implement the StatePort connector when a real consumer is ready to use the exported evidence and the contract can be verified end to end. Keep actual State Card capture separate.

A universal SDK, an adapter marketplace, cloud services, LLM-generated explanations, a second extension, and a wholesale analyzer replacement are outside the initial alpha scope. Reconsider them only when a demonstrated requirement justifies the work.

## Working rules and progress

Keep one primary mechanism change in progress. Browser UI work may run alongside it with stable shared interfaces. Each work item identifies its supported claim, chosen cases, completion criterion, and remaining limits. Keep code, the relevant contract, and its verification together.

Track a small set of outcomes:

- Useful supported answers out of all preselected UI questions, with configuration and failure reasons.
- Incorrect asserted relationships found in those investigations.
- Independent installation and workflow completion, including assistance required.
- Time to the first supported conclusion when a comparable debugging task is available; record the method before making efficiency claims.

Keep the original six-case results separate from controls and new application cases. Test counts, artifact counts, and repository activity do not replace evidence of a useful supported workflow. Update this roadmap when a result changes the next decision; keep measured capabilities in [project status](docs/status.md).
